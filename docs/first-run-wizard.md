# TuneBox first-run wizard

The Raspberry Pi installer installs `daw-one-manager.service`. A real managed device that has not completed setup opens **Settings → Setup** on first use. The wizard can be revisited there later; it uses swipeable pages with mouse/keyboard and touch input. Completing setup records that choice on the device, not just in one browser.

1. **Netwerk:** inspect existing NetworkManager Wi-Fi interfaces, or enter a WPA personal SSID/password and explicitly connect. Ethernet may remain connected. If NetworkManager is absent, the wizard says so; use the OS network configuration instead. Changing Wi-Fi can disconnect the browser/SSH session. The password is cleared after the request and is never written to browser storage or passed as a command-line argument.
2. **Music Assistant:** enter a local server address and token. Connection/authentication is tested with the existing MA transport and `players/all`. Public internet addresses and credential-bearing URLs are rejected. An empty token keeps the existing standard token file when present.
3. **Speler:** explicitly choose an available player returned by that test. Default is read only, with an explicit control opt-in and volume ceiling of 40%. Saving writes `/etc/daw-one/connection.env` and the protected token file, then restarts only the backend. Existing `/etc/daw-one.env` is preserved; the connection drop-in loads after it. No playback command is sent by setup.
4. **Audio:** explicitly consent to a short headphone-output voice test at a low listening volume. Only the Raspberry Pi bcm2835 Headphones device is eligible. An occupied output is not taken over and Squeezelite is not stopped. HAT/other DAC outputs remain blocked. This test does not change Squeezelite's configured output; select/configure other outputs separately after hardware verification.
5. **Sensoren:** show current PCT2075 and TSL2591 telemetry, rounded for display. Missing, stale, offline or uninstalled sensors are not treated as zero or as passed. The amplifier remains unverified.
6. **Afronden:** record setup completion. Optional missing hardware does not prevent demonstrating the interface; finishing never enables an amplifier or marks hardware validation complete.

Network/audio/connection changes require idle playback and safe state. If the current live player/server is unreachable, stop/repair the connection through the existing service configuration before issuing these operations; an unknown live state is not treated as safe idle. In development simulation the same action protocol is exercised but changes are visibly simulated, no credentials are persisted, and no real Wi-Fi, audio or MA configuration is changed.

The device manager accepts a fixed JSON command protocol through a Unix socket accessible to the backend service group. The browser reaches it through `/api/device`, with a process-bound control token and same-origin checks. There is no arbitrary shell, file-path or GPIO command endpoint. The independent HTTP progress port is read only. Keep the application bound to loopback and use an SSH tunnel for remote setup; this is device-local administration, not an authenticated public internet management service.

Real Wi-Fi, systemd restarts, headphone playback and saving credentials must still be validated on a Raspberry Pi. A successful mock/browser run does not certify these hardware operations.
